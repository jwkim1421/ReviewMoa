# P1-1 분석 정확도·신뢰도 개선 — 설계 (Spec)

> 작성일: 2026-08-15 · 계획서 항목: P1-1 (`next-step-upgrade-plan.md`)

## Context (왜)

리뷰모아 보고서의 "신뢰도" 점수는 **구매 만족도가 아니라, 결론을 뒷받침할 리뷰
데이터가 얼마나 충분·일관적인지**를 나타낸다. 그러나 현재 화면은 이 구분을 접힌 상세
안에서만 설명하고, 각 점수가 왜 그렇게 나왔는지(차감 사유)를 보여주지 않아 사용자가
"신뢰도 = 상품 품질"로 오해할 수 있다. 또 광고성/중복/평점 불일치 분류는 완전 동일
문장·단순 키워드 기준이라 근접 중복과 한국어 부정 표현을 놓친다.

참고: 신뢰도 **5요소 산식(완성도 35·근거 25·반복 20·최신성 10·건전성 10)은 이미
`worker/src/analyze.ts`에 실제로 구현**되어 있다(HANDOFF의 "고정 15점" 문제는 해결됨).
따라서 이번 작업은 산식 재작성이 아니라 **설명·버전 기록·오해 방지 + 분류 정확도
보강**이다.

## 범위

두 파트로 나뉘며 배포 대상이 다르다.

- **Part A (웹/Worker)** — 즉시 배포(Pages/Worker), 재빌드 불필요.
- **Part B (확장 `content.js`)** — 다음 TestFlight 빌드에 포함(운영자 실기기 테스트와 함께).

## Part A — 신뢰도 설명·버전·만족도 구분

### A1. 산식 버전 기록
- `createReport`가 보고서에 `confidenceVersion: "2026-08"`를 추가한다.
- 화면의 "신뢰도 계산" 상세 우측 상단에 `산식 v2026-08`로 표시.
- 구형 캐시 보고서(필드 없음)는 버전 태그를 숨긴다(하위호환).

### A2. 요소별 차감 사유
- `confidence()`가 5요소 점수와 함께 **짧은 사유 문자열**을 계산해
  `confidenceExplanations: { completeness, evidence, consistency, freshness, health }`
  로 보고서에 담는다. 사유는 원 신호(별점별 수집 대비, 리뷰 수, 반복 강도, 작성일
  분포, 제외 수)에서 파생한다. 예:
  - 완성도: "일부 별점이 원본 대비 덜 수집됨" / "모든 별점을 원본 수준으로 수집"
  - 최신성: "리뷰 대부분이 1년 이상 전에 작성됨" / "최근 6개월 리뷰가 다수"
  - 건전성: "제외 신호 없음 (0개가 진위를 보증한다는 뜻은 아님)"
- 화면: "신뢰도 계산" 상세를 **점수 + 사유** 2열로 표시. 점수 열은 점수 폭에 맞추고
  점수와 사유 사이 간격은 **`column-gap: 32px`**. 사유 필드가 없으면(구형 보고서)
  기존 요소명만 표시(하위호환).

### A3. 신뢰도 ≠ 만족도 구분 (상시 노출)
- 신뢰도 링 옆 라벨을 **"데이터 신뢰도 · 높음/보통/낮음"** + 작은 태그 `데이터 충분성`.
- 링 옆에 **상시 문구**(접힘 없이): "상품이 좋고 나쁨이 아니라, 이 결론을 뒷받침할
  리뷰 데이터가 얼마나 충분하고 일관적인지를 나타냅니다."

### A 변경 파일
- `worker/src/analyze.ts` — `confidence()` 사유·버전 계산, `createReport` 필드 추가.
- `worker/src/analyze.test.ts` — 버전·사유·집계 회귀.
- `src/domain/types.ts` — `confidenceVersion?`, `confidenceExplanations?` 타입.
- `src/App.tsx`, `src/styles.css` — 카드 라벨·상시 문구·상세 2열(32px)·버전 태그.

## Part B — 분류 정확도 (확장)

핵심 원칙: **보수적**. 잘못 제외(false exclude)보다 포함이 낫고, 평점 불일치는 허위가
아니라 "의심 신호"로만 다룬다.

### B1. 근접 중복 강화
- 현재: `fingerprint()`(소문자·영숫자·한글만, 1200자)로 **완전 동일**만 `duplicate`.
- 변경: 본문을 **강하게 정규화**(공백·문장부호·반복문자 축소)한 뒤, **앞부분 일정
  길이(시작값 40자) + 대표 토큰 집합**으로 "근접 키"를 만들어 **같은 키끼리 중복
  처리**. 정확한 길이·토큰 수는 구현 계획에서 확정하고 fixture로 오탐을 조정한다.
- 성능: 모바일에서 최대 3000개를 O(n)으로 처리(쌍별 O(n²) 비교 없음). 기존
  `duplicateBodies` Set 구조를 근접 키 Set으로 확장.

### B2. 평점·본문 불일치 보수적 개선
- 현재: 긍정/부정 키워드 개수 비교.
- 변경: **한국어 부정 표현** 반영(예: "좋지 않다/별로다/좋진 않아"는 '좋'이 있어도
  부정으로). 신호가 약하거나 상충하면 `rating_mismatch`로 단정하지 않고 `uncertain`
  으로 둔다.

### B 변경 파일
- `extension/content.js` — 근접 키 생성·중복 판정, 부정 표현 반영 불일치 규칙.
- `extension/content.test.ts` — 근접 중복(살짝 다른 문장) 처리, 부정 표현 판정.

## 배포·검증
- Part A: master push → GitHub Pages(웹) + `wrangler deploy`(Worker). 마이그레이션 없음.
- Part B: `safari:release:prepare` → archive/export → TestFlight 빌드.
- 완료 기준(계획서 P1-1): 신뢰도 각 구성요소를 화면에서 개별 설명 가능, 산식 버전
  기록, 신뢰도/만족도 구분, 같은 fixture에서 로컬/Worker 집계 일치, 근접 중복·부정
  표현 케이스 테스트 통과.

## Out of scope (이번 이터레이션 제외)
- 신뢰도 산식 자체의 가중치 변경(이미 구현·검증됨).
- 상품군별 전용 분류 규칙, AI 기반 군집화(별도 P 항목).
- 분석 근거 원문 연결(P1-2), 옵션별 분석(P1-3).
